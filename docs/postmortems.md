# 오류·판단미스 이력

> 원인 → 무엇을 했나 → 결과 → 남은 위험. **고친 뒤에도 지우지 않는다** — 근거가 사라지면 같은 판단을 또 한다.

## 경계 타일이 5분에 502 를 297번 냈다 (2026-08-23)

**무슨 일** — 배포하자마자 Vercel 알림이 왔다. `/map/bnd/[z]/[x]/[y]` 에서
**5xx 297건 / 5분** (평소 하루 평균 1건). VWorld WMS 가 실패하고 있었다.

**왜 그렇게 커졌나** — 우리 쪽 결함이 셋이었고, 셋이 서로를 키웠다.

1. **`cache: "no-store"`** — 같은 타일도 사람마다 새로 VWorld 를 불렀다.
2. **실패를 502 로 올렸다** — 지도는 타일을 **수십 장 한꺼번에** 부른다.
   한 번 막히면 5xx 가 수백 개가 된다. 알림이 울리고, **진짜 장애가 그 소리에 묻힌다.**
3. **실패를 캐시 안 했다** — 브라우저가 곧바로 다시 부른다. **막힌 쪽을 더 세게 때린다.**

**무엇을 했나**
- 성공 타일은 `next: { revalidate: 86400 }` 로 하루 둔다. 같은 타일은 VWorld 를 안 간다.
- 실패하면 **투명한 1×1 PNG 를 200 으로** 낸다. 경계만 안 보이고 지도는 멀쩡히 돈다.
- 빈 타일도 **1분 캐시**한다 — 막힌 동안 두들기지 않는다.
- 응답이 그림이 아니면(오류 XML 이 200 으로 오기도 한다) 그것도 빈 타일로 둔다.

**교훈** — ⛔ **바깥이 막힌 것을 우리 5xx 로 올리지 않는다.**
우리가 못 고치는 실패를 우리 오류로 세면 **알림이 무뎌지고 진짜 장애를 놓친다.**
⛔ **실패는 성공보다 더 캐시해야 할 때가 있다** — 안 그러면 재시도가 곧 공격이 된다.
⚠️ 다만 **삼키는 것과 다르다**(§11-2). 타일은 화면이 「실패했다」고 말할 자리가 없으므로
까닭을 `x-bnd-error` 헤더와 서버 로그에 남긴다.

**남은 위험** — VWorld 가 왜 막혔는지는 모른다. 개발용 키의 초당·일일 상한일 수 있다.
⛔ 오픈 전에 **운영용 키로 바꾸고 도메인을 등록해야 한다**(`DESIGN.md §12 열린 것 ㉙`).

## 빈 마이그레이션이 「적용 성공」으로 지나갔다 (2026-08-23)

**무슨 일** — 「등교」를 「출근」으로 고치는 마이그레이션을 올렸고 `supabase db push` 가
`{"migrations":["20260822174709_commute_dir_rename.sql"],"message":"Finished"}` 를 냈다.
**그런데 아무것도 안 바뀌었다.** 파일이 **0바이트**였다.

**왜** — 그 파일을 셸 heredoc(`cat > "$(ls …)" <<'SQL'`)으로 썼는데, 같은 명령줄 끝에 붙인
`supabase db push` 가 5분 제한에 걸려 명령 전체가 죽었다. 파일은 만들어졌고 내용은 안 들어갔다.
그 뒤 재시도한 `db push` 는 **빈 파일을 정상적으로 적용**했다 — 빈 SQL 은 오류가 아니다.

**어떻게 알았나** — 믿지 않고 **결과를 쟀다.**

```
방향 값     {'퇴근': 2, '등교': 20}     ← 「출근」이 하나도 없다
「등교」 넣기 → 성공                      ← 제약이 안 걸려 있다
```

제약이 있었다면 20줄의 「등교」가 남아 있을 수 없다 — **그 모순이 단서였다.**

**무엇을 했나** — 새 마이그레이션을 **파일 쓰기 도구로** 만들고(heredoc 안 씀) 올린 뒤,
다시 재서 확인했다 — 출근 21 · 퇴근 2, 「등교」 넣기는 `23514` 로 막힌다.
빈 파일은 원격 장부에 남아 있으므로 지우지 않는다(다시 못 쓴다).

**교훈** — ⛔ **긴 내용을 셸 heredoc 으로 파일에 쓰지 않는다.** 명령이 중간에 죽으면
빈 파일이 남는데, 빈 파일은 **어느 단계에서도 오류가 아니다.**
⛔ **`db push` 가 성공했다고 스키마가 바뀐 게 아니다.** 바뀐 것을 **직접 재서** 확인한다 —
제약이면 위반을 한 번 넣어 보고, 값이면 세어 본다.
⚠️ 나이스 5행 · Supabase 1,000행 · 「한 번도 적용된 적 없던 CSS 규칙」과 **같은 종류**다 —
오류가 안 나고 화면도 멀쩡한 채로 아무것도 안 한다.

**남은 위험** — `supabase db push` 가 5분 넘게 멈추는 일이 두 번 있었다. 왜인지는 모른다.
멈추면 **다시 돌리기 전에 파일 크기부터 본다.**

## CSS 규칙 하나가 한 번도 적용된 적이 없었다 (2026-08-23)

**무슨 일** — 폰에서 **지도 확대·축소 단추가 아래 시트에 가려** 안 눌렸다.
`globals.css` 에 「폰에서는 108px 띄운다」는 규칙이 **적혀 있었는데도** 그랬다.

**왜** — maplibre 의 `.maplibregl-ctrl-bottom-right { bottom: 0 }` 와 **특이도가 같았고**(둘 다 클래스 하나),
maplibre 의 CSS 가 **뒤에 실린다.** `globals.css` 는 `app/layout.tsx` 가 부르고
`maplibre-gl.css` 는 **부품**(`components/map/map-screen.tsx`)이 부르는데, Next 는 부품 쪽을 뒤에 싣는다.
같은 특이도면 **뒤가 이긴다.** 그래서 우리 규칙은 **한 번도 적용된 적이 없다.**

**어떻게 잡았나** — 빌드 산출물을 열어 두 규칙의 자리를 직접 쟀다.

```
globals.css   → /_next/static/chunks/3b1a…css   (먼저)
maplibre      → /_next/static/chunks/35rs…css   (뒤)  .maplibregl-ctrl-bottom-right{bottom:0;right:0}
```

**무엇을 했나** — 같은 클래스를 두 번 적어 특이도를 올렸다
(`.maplibregl-ctrl-bottom-right.maplibregl-ctrl-bottom-right`). **순서에 기대지 않는다.**
겸사겸사 시트 높이를 CSS 변수(`--sheet-h`)로 내보내 단추가 시트를 따라 올라가게 했다.

**교훈** — ⛔ **남의 라이브러리 클래스를 덮어쓸 때는 특이도를 한 겹 올린다.**
순서는 번들러가 정하고, 번들러는 우리 사정을 모른다.
⚠️ **더 큰 교훈** — 이건 **오류가 안 나는 결함**이다. 코드에 규칙이 적혀 있으니 읽으면 고쳐진 것처럼 보인다.
나이스 5행 · Supabase 1,000행과 같은 종류다 — **적어 둔 것과 도는 것을 대조해야 안다.**

**같은 꼴이 더 있나** — 그 자리에서 다 훑었다(§11-3). `globals.css` 가 덮어쓰는 maplibre 클래스는
셋뿐이고, 나머지 둘은 **다투지 않는다** — `.maplibregl-marker` 는 maplibre 도 같은 값(`will-change: transform`)을
걸고, `.maplibregl-ctrl-attrib` 에는 maplibre 가 `font-size` 를 안 건다. 확인 결과를 그 자리 주석에 적어 뒀다.

**남은 위험** — maplibre 를 올리면 원본 규칙이 늘어날 수 있다. 그때 이 셋을 다시 대조한다.

## 2026-08-19 · 스키마가 DB 안에만 있었다 (아슬아슬했음)

**무엇** — RUN_AWAY 를 얹을 Supabase 로 기존 프로젝트 **SUPATULA** 를 쓰기로 했는데, 그 안에
시수 편성 스키마(테이블 28 · 마이그레이션 7)가 살아 있었다. 전부 0행이라 "비었다"고 볼 뻔했다.

**판단미스가 될 뻔한 지점** — 로컬에 그 저장소가 **없었다.** `light_saber`·`slide-master`·`CommonSenses`
어디에도 없어서, 지웠으면 그 설계가 유일본째로 사라진다. 행이 0이라는 것과 잃을 게 없다는 것은 다르다.

**무엇을 했나** — 지우기 전에 마이그레이션 7개를 파일로 받아 `<private-local-path>`
에 두고, **DB 장부의 글자 수와 파일 글자 수를 1:1 대조**해 온전함을 확인한 뒤 걷어냈다.

**결과** — `public` 테이블 0 · 함수 0 · `private` 스키마 없음 · 장부 0행 · 확장 3개 무사.

**교훈** — ⛔ **DB 를 비우기 전에 "이 스키마의 원본이 어느 저장소에 있나"를 먼저 찾는다.**
없으면 그 DB 가 원본이다. 그리고 백업은 **뜬 것으로 끝내지 말고 원본과 수치로 대조**한다.

**남은 위험** — `public` 에 확장이 없어서 전부 지워도 안전했다. 다음에 같은 일을 하면
`pg_extension` 을 **먼저** 확인한다(확장이 `public` 에 있으면 같이 날아간다).

## Supabase 가 1,000행에서 조용히 끊었다 (2026-08-20)

**무슨 일** — 학교 찾기 화면이 경기 초등 **1,367교 중 1,000교만** 보여주고 있었다.
홈의 구역별 집계도 갑 893 이 **730** 으로 나왔다. 오류는 없었고 화면도 멀쩡했다.

**왜** — PostgREST(Supabase)는 한 번에 **1,000행**만 준다. `.limit(3000)` 을 걸어도 1,000 에서 끊고
**오류를 내지 않는다.** 클라이언트 limit 으로는 서버 상한을 못 넘는다.

```ts
.select("...").limit(3000)   // → 1,000행만 온다. 오류 없음
```

**어떻게 알았나** — 화면 숫자와 DB 를 직접 대조하다 걸렸다. 대조하지 않았으면 못 봤다.

**고친 것**
1. `.range(from, to)` 로 끝까지 넘겨 받는다.
2. `{ count: "exact" }` 로 **서버가 세어 준 총계를 함께 받아 개수를 맞춰 본다.** 안 맞으면 던진다.

**교훈** — `CLAUDE.md §11-1`(침묵 상한 금지)은 우리가 쓰는 코드만이 아니라 **쓰는 라이브러리에도 있다.**
바깥에서 목록을 받아 오면 **받은 개수를 반드시 총계와 맞춰 본다.** 나이스도, 학교알리미도 같은 함정이 있었다
(인증키 없이 부르면 5행만 온다). 셋 다 오류를 내지 않는다.

## 항목 이름을 값과 다르게 붙였다 — 그 이름을 믿고 사장님께 틀린 보고를 했다 (2026-08-20)

**무슨 일** — 지도에 안 찍히는 학교 12곳을 두고 사장님께 **"전부 최근 개교한 신도시 학교"** 라고
보고했다. 사장님이 되물었다 — "개교 한 건가 이미? 아니면 예정인 건가?"
다시 보니 **절반이 틀렸다.** 동탄초는 **1923년** 개교, 영천초 2015년, 여울초 2021년이다.

**왜** — 나이스에서 `FOAS_MEMRD` 를 받아 `closedAt`(폐교일)이라고 이름 붙였다.
그 항목은 실제로는 **개교기념일**이다. 나이스는 폐교를 따로 알려 주지 않고 **이름에** 적어 온다
("전곡초등학교적동분교장(폐교)"). 나는 내가 붙인 이름을 믿고 값을 안 봤다.

**두 번째 미스** — 2027학년도 신설교 7곳이 대조 결과의 `notInNeis` 에 있길래
"[별표1] 인사구역 표에 없다"고 단정했다. 실제로는 **별표1에 이미 실려 있고 구역까지 정해져 있다**
(6교 전부 을구역). 나이스에 아직 표준학교코드가 없어서 그쪽으로 빠진 것이었다.
결과 파일의 한 칸만 보고 원본 표를 안 봤다.

**무엇을 했나**
- `closedAt` → `openedOn` 으로 이름을 바로잡고 왜 헷갈렸는지 주석에 남겼다. 쓰는 곳은 한 곳뿐이라 번지지 않았다
- 대조 결과에 `opensSoon` **값**을 넣었다. 왜 빠졌는지를 문장으로만 남기면, 문구를 고치는 순간 조용히 어긋난다
- 신설교 6곳을 `opens_year` 로 갈라 담고 화면에서 따로 세웠다

**교훈** — ⛔ **바깥에서 받은 항목은 이름을 지어 붙이기 전에 값을 눈으로 몇 건 찍어 본다.**
날짜는 특히 쉽다. 폐교일이라면서 1923년이 나오면 그 자리에서 드러난다.
⛔ **"목록에 없다"고 말하기 전에 원본 표를 본다.** 중간 산출물의 한 칸은 "여기서 빠졌다"만 말하지,
"어디에도 없다"를 말하지 않는다.

**남은 위험** — 나이스에서 받아 오는 다른 항목(`kind`·`founded`·`branch`)도 같은 방식으로
이름만 보고 믿고 있다. 쓰기 전에 값을 한 번씩 찍어 본다.

## 인천 「인사구역」을 「급지」라고 이름 붙였다 — 다른 값인데 (2026-08-20)

**무슨 일** — 인천 인사구역 Ⅰ·Ⅱ·Ⅲ 을 화면에서 **가·나·다 급지**로 바꿔 적었다.
사장님이 잡았다 — "인천 쪽은 우리가 매칭한 급지가 다 틀렸어. 같은 학구라도 가나다가 다른데
부평은 죄다 '가'로 나오더라."

**왜 틀렸나** — 둘은 **다른 값**이다. 고시문 스스로가 그렇게 쓴다.
- 제8조 「**인사구역**은 (별표1)과 같이 Ⅰ구역, Ⅱ구역, Ⅲ구역 등 3구역으로 설정한다」
- 제24조 「다만, 동일구역 내 학교의 **급지 지정**과 … 은 교육장이 조정·실시할 수 있다」

즉 **급지는 인사구역 안에서 다시 갈리는 값**이고, 그 표는 **교육지원청 세부기준**에 있다.
부평은 전부 Ⅰ구역이지만 그 안에서 가·나·다 급지가 갈린다.
교사가 전보 때 쓰는 말은 그 급지다 — 「가급지에 있던 사람은 가급지로 못 간다」 같은 규칙이 붙는다.
Ⅰ·Ⅱ·Ⅲ 은 파견·도서벽지처럼 특수한 자리를 가르는 값으로 보인다.

**내가 뭘 잘못했나** — 사장님이 "급지를 로마자로 표기하지 말고 가,나,다로 표기해줘"라고 했을 때,
**「Ⅰ·Ⅱ·Ⅲ 을 가·나·다로 바꿔 부르라」는 뜻으로 읽고 그대로 바꿨다.**
그 말이 「우리가 안 가진 다른 값을 보여 달라」는 뜻일 수 있다는 걸 확인하지 않았다.
바로 앞에서 **제24조가 급지를 교육장에게 넘긴다는 것을 내 눈으로 읽어 놓고도** 이어 붙이지 못했다.

**무엇을 했나** — 원문 그대로 Ⅰ·Ⅱ·Ⅲ 로 되돌렸다. 화면·필터·계산기 전부.
급지 자료가 생기기 전에는 급지라는 말을 화면에 쓰지 않는다.

**교훈** — ⛔ **표기를 바꾸라는 말과 다른 값을 보여 달라는 말은 다르다.**
같은 낱말(「급지」)이 원문에서 다른 것을 가리키고 있으면, 바꾸기 전에 그 낱말이
원문 어디에 어떻게 쓰였는지 먼저 센다. 이번엔 제24조에 답이 있었다.
⛔ **내가 방금 읽은 조항을 다음 판단에 못 쓰면 읽은 게 아니다.**

**남은 위험** — 경기 병구역 급지(가·나·다·라)는 **별표1 표 안에 있어서** 확인된 값이다.
인천 것만 없다. 둘을 같은 화면에서 「급지」라 부르지 않도록 주의한다.


## 같은 이름 학교에 다른 지원청 급지가 붙었다 (2026-08-21)

**무슨 일** — 인천 급지를 학교에 붙일 때 **이름만으로 맞췄다.** 강화 삼산초가 북부 표의 「삼산」에 걸려,
**아직 고시가 안 난 강화 학교에 급지가 생겼다.** 화면에는 「나급지」로 멀쩡히 보였을 것이다.

**어떻게 잡았나** — 세어 보는 검산이 잡았다. 급지가 붙은 학교가 178교여야 하는데 179교였고,
「?」로 남아야 할 학교가 92 대신 91이었다. **숫자가 하나 어긋난 것 말고는 아무 증상이 없었다.**

**왜 틀렸나** — 인천에는 같은 이름의 학교가 여럿이다(삼산·동암·검단…). 급지 표는 **지원청별로 갈라져** 있고
이름은 그 안에서만 유일하다. 표 전체를 한 사전으로 합치는 순간 그 경계가 사라진다.

**무엇을 했나** — **지원청까지 맞을 때만** 붙이도록 고쳤다(`scripts/assign-incheon-areas.mjs`).
그리고 검사를 양쪽으로 걸었다 — ① 고시가 난 지원청인데 급지가 없는 학교 ② **고시 전인데 급지가 붙은 학교.**
둘 중 하나라도 걸리면 `EXIT=1`.

**교훈** — ⛔ **이름은 열쇠가 아니다.** 같은 이름이 여럿인 판에서는 「이름 + 그 이름이 유일한 범위」가 열쇠다.
같은 실수를 학교알리미에서도 했었다(이름만으로 이으니 14곳이 안 붙었다 — 「정식 이름 + 교육지원청」으로 고쳤다).
⛔ **검산은 양방향으로 건다.** 「있어야 할 게 없나」만 세면 「없어야 할 게 있는」 쪽은 그냥 지나간다.


## 네이버 Directions 가 `departureTime` 을 조용히 버렸다 (2026-08-21)

**무슨 일** — 통근 소요시간을 「내일 아침 8시 기준」으로 받으려고 `departureTime=2026-08-22T08:00:00` 을 실어 불렀다.

```
응답  HTTP 200 · code 0 · "길찾기를 성공하였습니다"
      departureTime: 2026-08-21T09:37:44     ← 부른 시각. 요청한 08:00 이 아니다
```

**오류를 안 낸다.** 성공이라고 답하면서 파라미터를 버리고 **현재 시각 교통**으로 계산한다.
문서로도 확인했다 — Directions **5도 15도** 출발·도착 시각 파라미터가 없고 실시간 교통만 반영한다.

**왜 속기 쉬웠나** — 네이버 지도 **앱**에는 도착시각 예측이 있다. 앱에서 되는 것과 파는 API 가 다르다.
그리고 모르는 파라미터를 거절하지 않고 무시하는 API 는, 코드만 보면 잘 도는 것처럼 보인다.

**무엇을 했나** — 시각 지정을 포기하고 **그 시간대에 실제로 재서 남기는** 쪽으로 설계를 바꿨다
(`DESIGN.md §12-54·56`). 값에는 **잰 날짜와 기준 시간대**를 반드시 같이 적는다.

**교훈** — ⛔ **바깥 API 는 「받아 줬나」가 아니라 「반영했나」로 확인한다.**
응답 안에 되돌아오는 값(여기서는 `departureTime`)을 **요청한 값과 대조**해야 안다.
같은 모양을 이미 두 번 겪었다 — 나이스는 키 없이 부르면 5행만 오고, Supabase 는 1,000행에서 끊는다.
셋 다 **오류 없이 조용히 모자란다.**


## 2026-08-23 — `isStyleLoaded()` 가 길찾기 경로를 조용히 버렸다

**증상** — 사장님: 「길찾기도 지금 눌러보면 경로가 안그려지넹」. 오류는 없다. 목록도 뜨고
상세보기도 열리는데 지도에만 선이 안 그려진다. 어쩌다 한 번은 그려진다.

**원인** — 경로를 받는 자리에 문지기가 하나 있었다.

```js
const on = (e) => {
  const m = map.current;
  if (!m || !m.isStyleLoaded()) return;   // ⛔ 여기
  ...
};
```

`isStyleLoaded()` 를 「스타일이 준비됐나」로 읽고 쓴 것이 틀렸다. maplibre 의 `Style.loaded()` 는
`_loaded` 뿐 아니라 **등록된 모든 source 의 타일이 지금 다 받아졌는지**까지 본다.
배경 지도(VWorld) 타일은 지도를 조금만 움직여도 새로 받으므로 이 값은 **수시로 `false`** 다.
그 사이에 경로를 누르면 알림이 버려졌고, **다시 보낼 길이 없어** 영영 안 그려졌다.

⛔ **§11-2 와 같은 꼴이다** — 화면이 실패를 버렸고, 사용자는 우리 서비스가 길을 못 찾는 줄 안다.
다른 점은 「서버가 실패를 돌려준 것」이 아니라 **「받는 쪽이 아직 준비가 안 됐다고 스스로 판단해
버린 것」**이라는 데 있다. 결과는 같다.

**고친 것**
1. 요청을 `wantLine` ref 에 **남긴다.** 버리지 않는다.
2. `paintRoute()` 는 `getSource("route")` 가 있느냐만 본다 — `setData` 는 타일이 받아지는
   중에도 안전하다. **필요한 조건과 잰 조건이 달랐던 것**이 이 사고의 전부다.
3. 자리가 아직 없으면 `ready` 가 서는 순간 다시 그린다.

**같은 종류를 더 찾았나** — `grep -rn "isStyleLoaded" components lib app` 으로 훑었다.
남은 사용처는 없다.

**배운 것** — ⛔ **문지기를 세울 때는 「필요한 조건」을 세워라.** 「대충 준비됐나」로 읽히는
함수를 갖다 쓰면, 그 함수가 실제로 무엇을 재는지와 어긋난다. 그리고 문지기에 걸려 버려지는
것이 사용자의 요청이면 **버리지 말고 남겨 두었다가 다시 해라.**

## 2026-08-23 — `supabase db push` 가 **빈 마이그레이션**을 오류 없이 올렸다

**무슨 일** — 익명 사용자가 닉네임을 선점하지 못하게 막는 마이그레이션을 만들어 올렸다.
CLI 는 `Applying migration 20260823070704_nickname-not-for-guests.sql…` 을 찍고 성공했다.
그런데 **정책은 안 바뀌어 있었다.** 파일이 **0줄**이었다.

**왜 안 보였나** — 한 번의 명령 안에서 ① 마이그레이션 파일 만들기 ② 내용 쓰기 ③ push 를
이어 붙였는데, ②가 비어 있는 채로 ③이 돌았다. `supabase db push` 는 **빈 파일을 정상으로 보고**
적용 이력에만 기록한다. 오류도 경고도 없다. 그 뒤로는 이력에 「적용됨」으로 남아서
**파일을 채워 다시 올려도 아무 일도 일어나지 않는다.**

**어떻게 잡았나** — SQL 을 믿지 않고 `pg_policies` 를 직접 읽어 보았다. 규칙이 옛 모습 그대로였다.

**고친 절차**
```
supabase migration repair --status reverted <버전>   # 이력에서 되돌린다
supabase db push                                     # 채운 파일이 다시 돈다
```

**규칙 둘**
- ⛔ **마이그레이션은 파일을 쓴 다음 줄 수를 확인하고 나서 올린다.** 쓰기와 올리기를 한 명령에 붙이지 않는다.
- ⛔ **올린 뒤에는 DB 에 물어서 확인한다.** `Applying migration…` 은 「파일을 읽었다」는 말이지
  「무언가 바뀌었다」는 말이 아니다. 정책·컬럼·함수를 `pg_policies` · `information_schema` 로 되읽는다.

### 이어진 사고 — **`npm run mig:new` 가 뒤따르는 heredoc 을 삼킨다** (같은 날 두 번)

위 사고를 적어 두고도 **또 났다.** 이번에는 이 꼴이었다.

```
npm run mig:new -- <이름>          ← 이 명령이 표준입력을 읽어 간다
cat > "$F" <<'EOF' … EOF          ← 그래서 여기 내용이 비어 버린다
supabase db push
```

빈 파일이 또 만들어졌다. 다행히 이번엔 push 가 시간 초과로 끊겨 원격에 안 남았다.

⛔ **규칙을 넓힌다 — 마이그레이션은 세 걸음을 따로 밟는다.**
1. `npm run mig:new -- <이름>` (여기서 끝낸다)
2. 파일을 쓴다 → **`wc -l` 로 줄 수를 확인한다**
3. `supabase db push` → **DB 에 물어서 바뀐 것을 되읽는다**

⚠️ `supabase db push` 는 원격 상태에 따라 몇 분씩 걸린다. 시간 제한을 넉넉히 준다
(2분으로는 모자란 것을 두 번 겪었다).

## 2026-08-23 — 학교알리미가 **남의 좌표를 준다** (파주 갈현초가 과천에 있었다)

사장님이 지도에서 찾았다 — 「과천 갈현초는 왜 갈현초로도 있고 갑,을 두개다 있는거임?」
과천에 말풍선 두 개가 겹쳐 있었다.

**두 학교가 맞다.** 과천갈현초(과천 · 안양과천 · 갑 · 1,119명)와 갈현초(**파주 탄현면** · 파주 ·
을 · 57명)는 서로 다른 학교다. 갑·을이 다른 것도 맞다.

**틀린 것은 좌표였다.** 둘의 위경도가 소수점까지 같았다(`37.4119107194, 126.9876424977` — 과천 자리).
파주 학교가 **42.7km 떨어진 과천**에 서 있었다.

**꼴이 하나다 — 이름이 짧은 학교가, 제 이름을 앞머리로 달고 있는 학교의 좌표를 받는다.**

| 잘못 찍힌 학교 | 진짜 있는 곳 | 받아 온 좌표의 주인 | 어긋남 |
|---|---|---|---|
| 갈현초 | 파주시 탄현면 | **과천**갈현초 | 42.7km |
| 대원초 | 성남시 중원구 | **파주**대원초 | 44.3km |
| 이동초 | 포천시 이동면 | **용인**이동초 | 79.1km |
| 중리초 | 포천시 관인면 | **이천**중리초 | 73.1km |
| 경수초 | 안산시 상록구 | 경일초 | 0.4km |
| 부발초백록분교장 | 이천시 두무재로 | 부발초 | 4.6km |

**우리 잘못이 아니다.** `fetch-schoolinfo.mjs` 는 학교코드(`SCHUL_CODE`)로만 붙이고 좌표는
`LTTUD`·`LGTUD` 를 그대로 쓴다. 이름으로 섞을 자리가 없다. **원자료가 그렇다.**
경기 1,409교 중 같은 좌표를 쓰는 무리가 8개(16교)였고, 그중 **주소가 다른데 좌표가 같은** 6개가
진짜 오류였다. 나머지 둘(보개초/가율분교장 · 서종초정배분교장/정배초)은 원자료 주소 자체가
같아 겹쳐도 사실이다. 인천 281교는 0건.

**어떻게 고쳤나** — 열두 곳을 제 도로명주소로 다시 지오코딩해서 200m 넘게 어긋난 여섯 곳만 옮겼다.
그중 인사구역 고시 표에 있는 둘(갈현초·이동초)만 `personnel_areas` 에 있어 DB 도 같이 고쳤다.

**막는 법 — `fetch-schoolinfo.mjs` 에 검산 둘을 넣었다.**
- ① **주소가 다른데 좌표가 같으면 양쪽 다 버린다**(`null`). 어느 쪽이 틀렸는지 알 수 없으니
  한쪽만 살리면 반은 틀린 채로 남는다. 비운 자리는 `geocode-missing.mjs` 가 주소로 채운다.
- ② **제 시·군 한가운데서 25km 넘게 떨어지면 세어서 적기만 한다.** ⛔ **버리게 만들었다가 물렀다** —
  섬 학교가 통째로 걸린다(옹진 백령 144km · 안산 풍도 45km · 화성 제부도 31km). 전부 제자리인데도.
  ①이 진짜 오류 여섯을 다 잡았고 ②가 더 잡은 것은 하나도 없었다.
  그래도 남긴 까닭은 **①은 틀린 좌표가 둘이 겹쳤을 때만 보이기 때문**이다. 한 곳만 엉뚱한 데로 간
  경우는 ②에만 뜬다.

**⛔ 내가 한 판단미스도 같이 적는다.** 원인을 찾는 도중 `fetch-schoolinfo.mjs` 를 읽었다고 **착각하고**
「환경변수 이름이 `SCHOOLINFO_KEY` 인데 `.env.local` 은 `SCHOOLINFO_API_KEY` 다」와
「학교알리미가 이제 `sggCode` 를 필수로 요구한다」를 사장님과 다른 세션 셋에 보고했다. **둘 다 틀렸다.**
파일은 이미 `SCHOOLINFO_API_KEY` 를 읽고 `sggCode` 도 붙이고 있었다. 내가 본 `fail` 응답은
**내가 손으로 만든 호출에 `sggCode` 를 안 넣어서** 난 것이다. 다른 세션이 실제로 17개 시·도를
불러 보고 정정해 주어 헛수고를 면했다.
⛔ **파일을 읽었다고 생각하면 그 출력을 다시 확인한다.** 특히 「원자료·바깥 API 가 바뀌었다」처럼
남의 일을 멈추게 하는 보고는 **파일과 응답을 눈으로 다시 보고** 말한다.
